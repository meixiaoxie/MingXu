# mingxu v0.1 发布门禁

> 复核日期：2026-07-28
>
> 当前结论：**未通过，不可发布，也不可对外宣称 v0.1 已完成。**

本文是 v0.1 的唯一发布判定清单。路线图描述开发顺序，本文只判断发布条件是否已经由证据满足。

## 1. 判定规则

- 所有“必须”项都为 `[x]` 才能发布。
- “部分完成”仍为 `[ ]`，只在下方记录进展和证据。
- 自动化测试通过不能替代人工在线 provider 验收；人工验收也不能替代自动化测试。
- 任何 secret、真实 Prompt、文件内容或模型响应都不得直接写入验收记录。
- 发布签核必须记录 commit、版本、Node/pnpm 版本、tarball integrity、测试链接和签核人。
- 本门禁不因计划日期、已有版本号或 package.json 中写着 `0.1.0` 而自动通过。

## 2. v0.1 冻结范围

### 2.1 必须交付

- TypeScript SDK 和本地 CLI。
- 内建 provider 的普通文本与 tool call。
- `AbortSignal`、操作 timeout、Run deadline 和有界 retry。
- 最大轮次、模型请求、工具调用、时间、token 和结果字节预算。
- 版本化 Run/Turn/Event、核心安全事件和内建 JSONL Audit。
- 版本化本地 Session 文件、原子写入和基础恢复。
- 可信本地 Tool 插件，仅稳定 `registerTool`。
- `mingxu init`、`mingxu doctor`、离线 E2E、真实 tarball smoke 和人工在线验收。

### 2.2 明确不交付

- provider、audit writer、session store、memory、policy、runtime 等正式 plugin API。
- plugin manifest、npm 插件安装、插件市场和插件间依赖。
- MCP、长期 Memory、RAG、Agent Preset、沙箱、调度、Workflow、多 Agent 和企业控制平面。
- streaming。

### 2.3 兼容但不稳定的入口

- `customProviders.module` 可以作为本地实验性兼容入口保留。
- 它不属于 v0.1 正式 provider plugin API，不获得相同的兼容承诺。
- 它与 Tool 插件一样是进程内可信代码，可以访问环境变量、文件、网络和 Node.js API。

## 4. 顺序门禁

以下分组与 `development-roadmap.md` 的 A-J 一一对应，必须按顺序通过。

### Gate A：范围与口径

- [ ] README、ADR、路线图、package 描述和本门禁对 v0.1 范围一致。
- [ ] ADR-002 使用 `trusted_local/blocked`，并明确进程内插件不是沙箱。
- [ ] ADR-004 的 Session/Run/Turn/Approval 定义和状态一致。
- [ ] streaming 明确不属于 v0.1，能力声明为 `supportsStreaming: false`。
- [ ] `customProviders.module` 明确标记为实验性。

通过证据：文档 review 链接或 commit。

### Gate B：公开契约与质量基线

- [ ] `--model <key>` 的实现、help、README 和测试一致。
- [ ] 源码和 tests 的 TypeScript typecheck 通过。
- [ ] 打包后公共类型消费 fixture 编译通过。
- [ ] PluginLoader 专门测试通过。
- [ ] 快速测试与 package smoke 分离，不重复执行。
- [ ] package smoke 不依赖固定 npm 安装目录。
- [ ] Node 22/24 的 CI 成功，跨平台测试成功。
- [ ] GitHub Actions 第三方 action 固定完整 commit SHA。

通过证据：CI URL、测试摘要、tarball smoke 日志。

### Gate C：运行实体与单一执行入口

- [ ] Run/Turn/Tool Invocation/Approval 类型和状态转换测试通过。
- [ ] 模型响应转换不丢 usage、stop reason、refusal 和 request id。
- [ ] 每次调用都有 run/turn/trace 关联 ID。
- [ ] Tool 只经 ToolExecutor 调用；Model 只经 ModelExecutor 调用。

通过证据：契约测试和状态机测试。

### Gate D：取消、超时、错误与重试

- [ ] provider fetch 和 Tool execute 均接收 AbortSignal。
- [ ] 用户取消、单次 timeout 和 Run deadline 均可终止实际操作。
- [ ] cancelled 与 timed_out 可区分。
- [ ] provider 错误具有稳定 code、retryable、status、request id 和安全 message。
- [ ] retry 支持 jitter、Retry-After、最大尝试、累计延迟和总 deadline。
- [ ] 认证、校验、内容过滤和部分输出不自动重试。

通过证据：每个内建 provider 和 Agent Loop 的失败注入测试。

### Gate E：预算与上下文

- [ ] 最大轮次、模型请求、工具调用、时间、token 和结果字节预算可强制停止 Run。
- [ ] usage 缺失被标记为 unknown/estimated，不被记为 0。
- [ ] 工具超大文本有明确截断标记。
- [ ] 结构化结果不会被截成非法 JSON。
- [ ] 大结果可转成受控 Artifact 引用。

通过证据：所有预算的边界测试。

## 5. 固定验收场景

### 5.1 自动化离线场景

在空临时目录中执行：

1. 从真实 `.tgz` 安装 `mingxu`，安装过程禁用 scripts。
2. 验证 `mingxu --help` 与 `mingxu --version`。
3. 从 package root 导入公共 JS API，并编译公共类型 fixture。
4. 运行 `mingxu init --profile minimal`。
5. 使用离线 mock provider 执行普通文本 Run。
6. 执行一个本地 Tool 插件的 tool call。
7. 验证预算、取消和 Policy deny 路径。
8. 验证 Session 文件与 Audit JSONL 已生成、可恢复且不含 secret canary。
9. 运行 `mingxu doctor` 并得到成功结果。

### 5.2 人工在线场景

使用临时、最小权限凭据：

1. `doctor --online` 明确提示网络访问与可能费用。
2. 至少一个内建 provider 返回普通文本。
3. 同一 provider 完成一次 `echo` 或等价低风险 tool call。
4. 操作者取消一个进行中的请求，Run 以 cancelled 结束。
5. 模拟 429/5xx，确认 retry 有界且 Audit 可追踪。
6. 删除临时凭据，只保存脱敏摘要、request id 和测试时间。

> 当前仓库已经提供可执行的命令、workflow 和签核模板，但真实在线验收仍需在拥有外部凭据与发布权限的环境里由人工执行并记录。

```text

```

普通 PR 不把付费、非确定性的在线模型调用作为强制条件；正式发布必须有一次受控人工在线验收。
