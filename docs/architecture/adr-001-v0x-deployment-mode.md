# ADR-001：v0.x 部署模式选择

- 状态：已批准
- 日期：2026-07-28
- 决策范围：`mingxu` v0.x CLI 与本地运行时

## 背景

`mingxu` 现在还是一个很轻的 TypeScript Agent Runtime 骨架。它的主要入口是 CLI，当前能力集中在：

- 读取本地配置
- 连接模型 provider
- 注册内置工具和插件工具
- 把一轮或多轮对话跑完
- 可选地把 session 写到本地文件

这时最先要回答的问题不是“以后会不会上云”，而是“v0.x 先按什么方式交付，才能让后面的安全、插件、会话和企业能力有稳定地基”。

如果部署模式一开始就不清楚，后面会出现几个问题：

1. 文档里不知道默认运行边界在哪里。
2. 插件权限和信任模型没法落地，因为不知道插件是跑在本机、容器还是托管服务里。
3. Session、文件访问、相对路径解析这些行为会变得含糊。
4. 初学者会搞不清“这个项目到底是库、命令行工具，还是一个一直在线的服务”。

所以 v0.x 需要一个非常明确、足够保守、也足够容易实现的默认部署模式。

## 决策目标

v0.x 的部署模式需要同时满足下面几件事：

- 足够简单，个人开发者几分钟内能跑起来
- 与当前代码结构一致，不要求先引入服务端控制平面
- 能为后续插件权限、审计、会话存储、企业沙箱预留演进空间
- 明确默认的 trust boundary（信任边界，也就是“默认相信谁，不默认相信谁”）

## 选项

### 选项 1：本地 CLI 进程模式

含义：

- 用户在本机通过 `mingxu` CLI 启动一次运行
- Agent Loop、provider 调用、工具执行、插件加载都在同一个本地 Node.js 进程里完成
- session 默认是本地文件或进程内存
- 配置、插件模块、相对路径都以本地文件系统为准

优点：

- 和当前代码最一致，实现成本最低
- 初学者最容易理解，像“运行一个命令行程序”
- 调试简单，问题定位直接
- 文档可以非常明确地说明文件、插件、配置都在本机边界内

缺点：

- 隔离能力弱，本地插件本质上就是本地代码执行
- 高风险工具和网络访问默认与宿主机共享边界
- 不适合直接宣称为多租户托管架构

### 选项 2：本地 CLI + 独立 sidecar/daemon 模式

含义：

- CLI 只是前端壳子
- 真正的 Agent Runtime 由本地常驻后台进程承载
- session、事件、策略都由后台进程统一管理

优点：

- 后续更容易接入多 session 管理和统一审计
- 可以逐步把权限控制集中到一个守护进程里

缺点：

- 对当前项目来说过早复杂化
- 安装、调试、跨平台进程管理都更难
- 需要额外定义 IPC（进程间通信）协议，超出 v0.x 最小目标

### 选项 3：远程托管服务模式

含义：

- 用户通过 CLI 或 SDK 访问一个远程 Agent service
- 模型调用、工具执行、插件加载、会话存储主要发生在服务端

优点：

- 更接近企业控制台和托管产品形态
- 统一审计、多租户、集中治理更容易做

缺点：

- 与当前仓库实现严重不匹配
- 要先解决认证、租户、服务部署、远程工具执行、数据边界等大量问题
- 会把原本清晰的“最小运行时骨架”变成“平台工程”

## 最终决策

选择“本地 CLI 进程模式”作为 `mingxu` v0.x 的默认部署模式。

也就是说，v0.x 应明确定位为：

> 一个默认在用户本机 Node.js 进程内运行的 CLI Agent Runtime。

## 决策理由

### 1. 它最符合当前代码现实

现在的核心链路是：CLI 解析参数，再把配置、模型、工具、插件、session 组合起来执行。这天然就是一个“本地命令启动一次运行”的结构。

### 2. 它能把系统边界讲清楚

v0.x 可以明确写成下面这套默认边界：

- `mingxu` 运行在本机
- 配置文件来自本机
- 插件模块来自本机文件系统
- provider 默认直接从本机访问外部模型 API
- session 默认保存在本机，除非以后显式接入别的存储

这对后面写插件安全、文件权限、secret 管理文档非常关键。

### 3. 它适合“先把地基做对”

v0.x 当前更需要解决的是：

- 核心与插件边界
- 插件信任模型
- Agent/Session/Run/Turn 数据模型
- Policy、Audit、Context、AbortSignal 等地基能力

而不是过早引入远程托管架构。

### 4. 它仍然保留后续演进空间

先选本地 CLI，不代表以后不能演进到：

- 本地 daemon
- 容器/沙箱执行器
- 企业托管控制平面
- 远程 session 与审计后端

只要核心协议保持中立，这些都可以在 v1+ 继续扩展。

## 具体落地约束

v0.x 文档和实现后续要遵守下面这些默认约束：

### 1. 运行边界

- 一个 `mingxu` 命令对应一次或一组本地运行
- 默认没有中心化控制平面
- 默认没有多租户隔离承诺

### 2. 存储边界

- session 默认是本地文件或进程内存
- 配置、插件、日志路径都以本地文件系统为主
- 相对路径应优先相对配置文件解析，而不是相对当前 shell 目录漂移

### 3. 权限边界

- 插件是本地代码执行，不应被表述成“安全沙箱”
- provider、tool、plugin 的网络和文件访问能力都默认共享宿主环境
- 企业级隔离要作为后续增强，不假装 v0.x 已经具备

### 4. 部署文档边界

README 和架构文档应把 v0.x 说清楚为：

- 适合个人开发、本地试验、受控企业 PoC
- 不默认等同于生产级多租户托管平台

## 数据流视角

v0.x 默认部署模式下，核心数据流如下：

1. 用户在本机执行 CLI 命令
2. CLI 读取本地配置文件
3. CLI 在本地进程中创建 provider registry、tool registry、plugin loader、session store
4. Agent Loop 调用远程模型 API
5. 模型返回文本或 tool call
6. 工具与插件在本地进程中执行
7. 结果回填到对话历史
8. session 可选写回本地文件
9. CLI 把最终结果打印到终端

## 后续影响

### 正面影响

- 文档可以统一口径，减少含糊说法
- 插件安全文档能基于真实边界写，而不是空想沙箱
- Session、Run、Audit 等模型设计可以先按本地 runtime 抽象
- 后续如果做企业增强，会更清楚哪些能力是新增层，不会误伤核心最小路径

### 代价与 trade-off

- v0.x 不提供强隔离承诺
- 需要在 README 和 ADR 中反复提醒“插件等于本地代码执行”
- 一些企业用户可能会问为什么不直接做托管服务，答案需要明确：当前阶段先把运行时协议和安全入口做稳

## 不做的事

这个 ADR 当前不决定：

- 企业托管控制平面的最终形态
- 多租户架构
- 容器或 VM 沙箱实现细节
- 远程调度和工作流编排系统

这些属于后续阶段的扩展议题。

## 复审触发条件

出现下面情况时，应重新评审这个 ADR：

- CLI 不再是主要入口，而是转为调用常驻本地守护进程
- 项目开始支持官方托管服务
- 插件需要默认运行在隔离容器而不是宿主进程中
- 企业功能成为主线，且本地单进程模式已经成为限制
