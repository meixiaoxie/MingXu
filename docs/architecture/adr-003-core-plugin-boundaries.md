# ADR-003：核心与插件边界

- 状态：已批准
- 日期：2026-07-28
- 决策范围：`mingxu` 核心运行时、内建模块与插件扩展点

## 背景

`mingxu` 的定位不是“把所有能力都内建进去”，而是做一个轻量、清楚、可扩展的 Agent Runtime 底座。

当前仓库已经有比较清晰的分层：

- `src/core`
- `src/models`
- `src/tools`
- `src/config`
- `src/plugins`
- `src/memory`
- `src/cli`

但“目录分开”不等于“边界已经定清楚”。如果不把核心与插件边界写成正式决策，后面很容易出现这些问题：

1. 某个需求来了，就随手塞进 core，最后 core 变成大杂烩。
2. 插件为了方便，开始绕过 ToolRegistry、ProviderRegistry 或 policy/audit 链路。
3. 文档里说“插件化”，但实际上很多关键能力没有稳定扩展点。
4. 后续接 MCP、企业策略、agent preset 时，会反复争论“这东西到底该放核心还是做插件”。

所以需要一个 ADR，把“核心一定负责什么、插件适合负责什么、什么能力不能被插件绕过”写清楚。

## 决策目标

- 让 core 继续保持轻量
- 保证扩展能力有稳定入口，而不是到处打洞
- 明确哪些能力必须放核心，哪些能力适合插件化
- 明确插件扩展不能绕过的底线

## 选项

### 选项 1：尽量内建，大部分能力直接进 core

优点：

- 用户开箱即用能力多
- 不用一开始就设计很多扩展点

缺点：

- core 很快变重
- provider、policy、memory、audit、preset 等都会耦合在一起
- 维护成本高，不利于初学者理解

### 选项 2：核心只保留运行时骨架，具体能力优先插件化

优点：

- 最符合项目目标
- 让 core 保持稳定、清楚、可测试
- 有利于企业按需装配能力

缺点：

- 需要先想清楚扩展点
- 某些用户会觉得“默认内建能力偏少”

### 选项 3：双轨制，大量能力同时提供 core 版和 plugin 版

优点：

- 对不同用户群灵活

缺点：

- 会造成重复实现
- 边界反而更模糊
- 文档和测试负担高

## 最终决策

选择“核心只保留运行时骨架，具体能力优先插件化”。

原则可以概括为：

> 核心负责统一协议、主执行链和安全兜底；插件负责增加具体能力，但不能绕过核心治理链路。

## 核心必须负责的能力

下面这些能力必须由核心负责，不能外包给插件主导：

### 1. Agent Loop 主循环

为什么放核心：

- 它是整个系统的“发动机”
- 负责模型调用、工具回填、轮次控制、错误传播、session 续写
- 如果每个插件都能改一套 loop，系统行为就不可预测

### 2. 统一消息与模型中立协议

为什么放核心：

- `core/types` 是全系统的共同语言
- 不能让某个 provider SDK 的格式渗透到全项目
- 否则插件、工具、memory、audit 都会被某个厂商协议绑死

### 3. Tool Registry 与 Provider Registry

为什么放核心：

- 工具和 provider 必须通过统一注册表接入
- 这样才能统一做重名检查、权限接入、审计接入和后续治理

### 4. Plugin Loader 与插件生命周期入口

为什么放核心：

- 插件要怎么加载、如何报错、何时注册能力，需要统一入口
- 否则不同插件会发展出不同的旁路加载方式
- v0.1 还需要由核心统一处理相对配置目录解析、`trusted_local/blocked`、风险提示和 setup 失败回滚

### 5. Policy、Audit、Event、AbortSignal 等基础治理入口

为什么放核心：

- 这些属于“保险丝”和“记录仪”
- 不能依赖某个插件是否自觉接入
- 插件可以扩展策略和写入器，但入口必须由核心控制

### 6. 基础配置加载与校验

为什么放核心：

- 配置是运行时装配入口
- 需要一致的 schema、默认值和错误提示

### 7. 基础 Session 接口

为什么放核心：

- session 是主循环的重要依赖
- 即使具体存储后端可替换，也要有统一接口和生命周期语义

### 8. 上下文预算与安全截断底线

为什么放核心：

- 避免工具结果、插件输出或 memory 内容把上下文撑爆
- 属于系统稳定性的最低保障

## 适合插件负责的能力

下面这些能力优先通过插件扩展：

### 1. 具体工具

例如：

- 文件工具
- Git 工具
- HTTP 工具
- 数据库工具
- 企业内部系统工具

原因：

- 不同用户需要的工具差异很大
- 放插件更灵活，也能把高风险能力单独治理

### 2. 具体 provider

尤其适合插件化的 provider：

- Azure
- Bedrock
- Ollama
- OpenRouter
- 企业内部模型网关
- 地区性模型平台

原因：

- 更新快、依赖差异大、权限需求高
- 没必要都塞进最小核心

### 3. 具体 policy 规则

例如：

- 个人开发宽松策略
- 企业保守策略
- 团队内部 allowlist 策略

原因：

- 核心只保留“授权入口”和决策协议
- 具体规则应可替换

### 4. 具体 audit writer

例如：

- 本地 JSONL
- HTTP 上报
- 企业日志平台

原因：

- 写入目标差异很大
- 核心不应绑定某一种后端

### 5. Memory 存储实现

例如：

- JSONL
- SQLite
- Postgres
- 企业知识库

原因：

- 存储介质因场景而异
- 统一接口即可，不必强塞实现进 core

### 6. Context compaction 策略

例如：

- 简单摘要器
- 工具结果裁剪器
- 面向企业审计保留的压缩规则

### 7. Agent preset

例如：

- 通用写作 Agent
- 代码助手 Agent
- 企业审批 Agent

原因：

- preset 是可装配能力，不应把所有 agent 角色写死在核心里

### 8. MCP 连接适配和安装说明

原因：

- MCP 更像标准外接插座
- 核心需要能接入，但具体 server 适配不必全部内建

## 内建与插件的推荐边界

v0.x 推荐这样划分：

### 建议继续内建在仓库主线中的内容

- 最小 Agent Loop
- 最小配置系统
- 最小 Plugin Loader
- 最小 Tool Registry
- 最小 Provider Registry
- 基础 session store（内存、本地文件）
- 少量适合联调的最小工具
- 少量常用 provider 适配器

### 建议优先插件化或后续插件化的内容

- 高风险工具
- 高依赖 provider
- 企业策略
- 企业审计写入器
- 长期 memory 存储
- 上下文压缩器
- agent preset
- MCP server 适配

## 不可绕过的边界

插件可以扩展系统，但不能绕过下面这些核心边界：

### 1. 不能绕过 ToolRegistry / ProviderRegistry

也就是说，插件不能私自藏一条“核心看不见的工具调用链”或“旁路模型调用链”来假装正常集成。

对 v0.1 Tool 插件来说，唯一稳定接入面是 `registerTool`。通过这个入口注册的工具，必须和内建工具共享同一个 `ToolRegistry`，再统一进入 ToolExecutor、Policy、Approval、Budget、AbortSignal 和 Audit 主链。

### 2. 不能绕过 policy

任何真正产生副作用的能力，比如：

- 文件读写
- 网络访问
- 命令执行
- MCP 工具调用

都应最终进入统一 policy 入口。

### 3. 不能绕过 audit / event

关键动作应可被记录。否则企业、开发者和调试者都看不见系统实际做了什么。

### 4. 不能绕过 AbortSignal

用户取消、超时取消、系统终止等控制信号应能沿统一链路传递。

### 5. 不能绕过上下文限制与 secret 脱敏

插件输出不能无限塞回模型；日志和错误也不能随意泄露 secret。

## 判断规则：一个能力该放核心还是插件？

后续遇到新能力时，优先按下面问题判断：

1. 它是不是运行时必备骨架？
   - 如果是，优先放核心。
2. 它是不是具体业务能力或具体后端？
   - 如果是，优先做插件。
3. 它是不是安全底线或治理入口？
   - 如果是，入口放核心，实现可插件化。
4. 它是不是高变化、高依赖、强场景化能力？
   - 如果是，优先插件化。

## trade-off

### 收益

- core 更轻，结构更稳
- 有利于后续并行开发和模块测试
- 企业能力不会把基础 runtime 挤变形
- 文档能更清楚地指导贡献者“改哪里合适”

### 代价

- 需要花时间设计扩展点
- 一部分功能前期不会默认内建
- 插件生态成熟前，用户可能需要多装一些能力

## 对后续阶段的影响

这个 ADR 直接支撑：

- 阶段 A：核心边界文档与 MCP 策略
- 阶段 C：policy、secret、插件 trust
- 阶段 D：event / audit / observability
- 阶段 E：plugin manifest、provider plugin、plugin 管理
- 阶段 G：memory 与 agent preset

## 不做的事

本 ADR 不直接规定：

- 某个插件 API 的最终 TypeScript 类型细节
- provider manifest 的最终 schema
- MCP connector 的具体配置字段
- 企业控制台的产品形态

这些要在各自专题设计中继续细化。

## 复审触发条件

出现下面情况时应重新评审：

- core 开始持续吸收大量具体业务能力
- 插件为实现需求而频繁绕开注册表或治理入口
- 项目决定内建大量官方插件并把它们视作核心一部分
- 引入远程执行平面，导致“插件”与“服务扩展”边界发生变化
