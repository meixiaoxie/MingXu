# ADR-002：插件信任与隔离模型

- 状态：已批准
- 日期：2026-07-28
- 决策范围：`mingxu` v0.x 插件加载、权限表达与后续安全演进

## 背景

`mingxu` 的一个核心目标是插件化。也就是说，后面很多能力不会都塞进 core，而是通过插件加进来，比如：

- 工具插件
- provider 插件
- memory 插件
- policy 插件
- audit 插件
- context compactor 插件
- agent preset 插件

但插件和普通配置不一样。插件本质上是“要执行的代码”。一旦运行，它可能：

- 读取环境变量
- 访问文件系统
- 发起网络请求
- 调用外部命令
- 注册高权限 provider 或工具
- 接触用户输入、系统提示词、工具结果和 session 数据

如果这里不先做架构决策，后面很容易出现两个极端：

1. 要么把插件包装得像“很安全”，但实际上插件和宿主进程几乎同权。
2. 要么过度承诺沙箱隔离，结果实现根本跟不上。

所以 v0.x 需要明确回答：

- 插件默认被当成什么等级的代码？
- 核心运行时应该提供哪些最小安全兜底？
- 后续的 allowlist、blocklist、ask approval、企业模式应该挂在哪里？

## 决策目标

这个 ADR 要解决的不是“把插件完全隔离起来”，而是先建立一套真实、可实现、可演进的信任模型，让后续权限与审计系统有统一基础。

目标包括：

- 不夸大 v0.x 的安全能力
- 清楚说明插件就是本地代码执行
- 为 `trusted_local / blocked`、Approval、权限声明和企业 allowlist 预留结构
- 保证所有“通过核心 API 发起的调用”都有统一的加载入口、授权入口和审计入口

## 选项

### 选项 1：默认全信任插件

含义：

- 只要用户配置了插件，就直接加载
- 不区分插件类型和信任等级
- 不要求权限摘要、allowlist 或审批概念

优点：

- 实现最简单
- 对个人开发者上手成本低

缺点：

- 很容易误导用户，像是在说“插件是普通扩展”，但实际上是执行第三方代码
- 企业无法建立治理规则
- 以后再补 trust 等级时，兼容成本更高

### 选项 2：声明式信任模型 + 最小运行时兜底

含义：

- v0.x 默认仍运行本地插件，但明确标记这是“本地代码执行”
- 插件具备 trust level（信任等级）概念
- 核心负责统一的加载入口、权限摘要入口、policy 授权入口、audit 事件入口
- 真正的强隔离先不承诺，但结构上为后续沙箱和企业治理预留位置

优点：

- 与当前项目阶段匹配
- 安全表述真实，不会假装已有沙箱
- 便于后续接入 allowlist、blocklist、审批和企业策略

缺点：

- 需要额外文档说明，不如“直接能跑”那样省事
- 用户可能会觉得限制比预期多，但这是必要的透明度成本

### 选项 3：默认强隔离沙箱插件

含义：

- 所有插件默认跑在受限容器、VM 或独立进程中
- 插件能力必须通过 IPC 或 RPC 暴露给 core

优点：

- 安全姿态最强
- 企业听起来最放心

缺点：

- 与当前项目体量严重不匹配
- 会引入大量平台工程与跨平台问题
- 很可能拖慢核心运行时演进

## 最终决策

选择“声明式信任模型 + 最小运行时兜底”作为 v0.x 的插件信任与隔离模型。

一句话概括：

> v0.x 的插件默认是本地代码执行，不承诺强沙箱；但核心必须提供统一的信任等级、授权入口、审计入口和后续隔离扩展点。

## 关键规则

### 1. 插件默认不是沙箱

文档必须明确告诉用户：

- 安装或加载插件，本质上等于执行该插件作者提供的本地代码
- v0.x 默认不把插件跑在容器、VM 或受限解释器里
- 因此插件来源必须可追溯、可审查、可控制

### 2. 先冻结 v0.x trust model，再谈加载策略

v0.x 先统一为两类有效信任结果：

- `trusted_local`：用户或组织明确允许加载的本地可信代码。它仍然不是沙箱，只是“允许这段本地代码进入当前进程执行”。
- `blocked`：禁止加载。即使出现在配置中，也应在真正导入插件模块前被拒绝。

在当前 v0.1 实现里，这个 trust model 已经落到插件配置上：

- `plugins: ["./plugins/my-tools.mjs"]` 会被归一成默认 `trusted_local`
- 也可以显式写成 `{ path, trust }`
- 相对插件路径按配置文件目录解析
- CLI 在加载前会输出来源和“加载插件等于执行第三方代码”的风险提示

这里要特别区分两个概念：

- **trust level（信任结果）**：回答“这段插件代码能不能加载”。
- **Approval（审批）**：回答“某次具体动作要不要临时确认”。

也就是说，v0.x 不再把 `prompt` 当成第三种 trust level。需要临时询问的情况，属于 Approval 流程，而不是插件信任等级本身。

### 3. 核心必须保留统一安全入口，但不能把进程内插件误写成“不可绕过”

即使插件被标记为 `trusted_local`，也不意味着它已经被隔离。后续实现里，核心仍应尽量把下面这些能力统一收口：

- policy：工具调用、文件访问、命令执行、网络访问、MCP 调用都应优先走统一授权入口
- audit/event：通过核心 API 发生的关键动作应能产生日志或事件
- AbortSignal：通过核心 API 发起的耗时操作应能响应用户取消和超时取消
- context limit：插件经由核心返回的内容仍受上下文预算和截断规则约束
- secret redaction：通过核心日志和错误链路输出的信息应经过脱敏

但文档必须说实话：

- 进程内本地插件可以直接访问 Node.js 能力、文件系统、网络和环境变量。
- 核心 API 只能治理“通过核心入口发起的调用”。
- 如果插件作者故意绕开核心 API，自行读文件、发请求或起子进程，v0.x 不能把这种旁路写成“被核心完全阻止”。

### 4. provider 插件风险高于普通工具插件

provider 插件会直接接触：

- 用户输入
- system prompt
- 工具结果
- 可能的 session 历史
- 网络出口与环境变量

所以 provider 插件的风险等级应高于普通 tool plugin。后续 manifest 和 policy 设计中，应至少要求 provider 插件声明：

- 会注册哪些 provider
- 需要访问哪些网络域名
- 需要读取哪些环境变量

### 5. 企业治理应基于 allowlist/blocklist，而不是模糊信任

后续企业模式应默认支持：

- allowlist：只允许明确批准的插件
- blocklist：明确禁止已知风险插件
- 权限摘要：加载前展示插件要做什么
- 审批记录：谁在什么时候批准了什么插件或权限

## 推荐的逻辑模型

### 信任结果模型

```text
requested source + local / organization policy -> effective trust
```

也就是说：

1. 配置或插件元信息可能提出一个期望等级
2. 本地策略或企业策略进行裁决
3. 运行时按最终生效等级执行

### 插件权限摘要模型

后续不管最终 manifest 怎么命名，都应能表达至少这些信息：

- 插件名称、版本、来源
- 插件类型：tool / provider / memory / policy / audit / context / preset
- 需要的能力：文件、命令、网络、环境变量、provider 注册
- 生效信任结果：`trusted_local` / `blocked`
- 是否需要某类 Approval 才能执行高风险动作

### 执行视角

虽然插件代码本身可能直接运行在本地进程中，但从架构约束上看，项目只应该把“通过核心扩展点接入系统的那部分能力”纳入统一治理，比如：

- 注册工具到 ToolRegistry
- 注册 provider 到 ProviderRegistry
- 注册 policy / audit / memory 扩展

这能保证通过核心入口接入的能力有统一约束；但不能把它写成“插件作者绝对无法在进程里自己绕开这些入口”。

## trade-off

### 收益

- 真实表达了 v0.x 的安全边界
- 为后续插件 manifest、企业 allowlist、审批、威胁模型留出清晰接口
- 避免“明明没有沙箱，却宣传得像隔离良好”的风险

### 代价

- v0.x 仍然无法提供强隔离保证
- 文档和 README 需要反复提醒插件风险
- 后续如果要做真正的沙箱隔离，还需要引入执行环境层

## 对实现和文档的直接影响

### 文档层

README 和架构文档应补充下面这些结论：

- 插件是本地代码执行
- v0.x 默认不做强隔离
- 企业如果要更强治理，应使用 allowlist、审批和后续沙箱方案

### 运行时层

后续实现应提供这些挂点：

- 插件加载前检查 trust level
- 插件加载前展示权限摘要
- 插件加载事件写入 audit/event
- 插件注册出来的工具和 provider 仍进入统一 policy 管道

### 配置层

后续配置应能表达至少：

- 启用哪些插件
- 插件来源
- 可选 trust 覆盖规则
- 组织级 allowlist/blocklist 或引用策略

## 不做的事

本 ADR 当前不直接定义：

- 插件 manifest 的最终 JSON schema
- 沙箱执行器的 API 细节
- UI 交互层的审批界面
- 插件市场或 npm 安装流程

这些属于后续阶段的落地议题。

## 复审触发条件

出现下面情况时，应重新评审：

- 插件开始默认在独立进程或容器中运行
- 项目引入正式的企业策略中心
- provider 插件支持远程托管执行而非本地加载
- 插件系统从“本地文件模块”升级为“可安装发行物 + manifest + 权限声明”的完整生态
